# DueGuard Notification Rules

## 전제
- 사용된 패키지: `flutter_local_notifications`.
- 타임존: **local device timezone only**. 사용자가 기기 타임존을 변경했을 때의 일관성은 MVP에서 보장하지 않는다. (앱 실행 시 보정 로직만 존재)
- 항목당 예약된 알림 수: **최대 1개 (다음 회차)**.
- 알림 ID 충돌 방지: `notificationId = item.id` 그대로 매핑 (Isar `Id`는 int이므로 그대로 사용 가능).

## 반복 규칙 (RepeatType 별 next occurrence 계산)

모든 계산의 기준 시각은 "이 회차의 `dueAt`"이다. `now`가 아니다.

### once
- 완료 시 다음 회차 없음. 항목은 리스트에서 사라지거나 "완료됨" 상태로 표시.
- 알림은 완료와 동시에 취소.

### daily
- `next = dueAt + 1 day`
- 시간(hour, minute)은 동일하게 유지.

### weekly
- `next = dueAt + 7 days`

### monthly
- `next = dueAt`의 "다음 달 같은 날짜".
- 에지 케이스:
  - 31일 → 30일 달에서는 30일, 2월에서는 28/29일로 **당겨서** 예약.
  - 29일(2월) → 평년에는 28일, 윤년에는 29일. 이후 회차는 다시 29일로 복귀하는 것이 맞지만, **MVP에서는 "마지막 유효 일자로 clamp"**만 구현한다. 즉 한 번 당겨졌다고 원래 날짜가 손상되지 않도록, 계산 기준은 **원래 생성 당시의 "의도 날짜(intended day)"**를 매번 참조한다.
- 구현 방법:
  - `dueAt`은 실제 예약 시각.
  - `intendedDay = 첫 등록 시 사용자가 선택한 day-of-month` (단, MVP에서는 별도 필드로 저장하지 않고 **"최초 dueAt의 day"**를 `createdAt` 시점 값으로 추적하는 방식으로 근사). 정확한 장기 운영을 위해서는 `anchorDay` 필드 추가를 고려하되, 우선은 "당겨진 경우 플래그 + 다음 달 계산 시 원본 day 복원 시도"로 대응.
- 요약: 사용자가 1/31을 선택하면, 2/28, 3/31, 4/30, 5/31 ... 로 가도록 한다.

### yearly
- `next = dueAt`의 "다음 해 같은 월/일".
- 에지 케이스:
  - 2/29 → 평년에는 2/28로 당겨 예약. 다음 윤년이 오면 다시 2/29로 복귀.
  - 이 역시 "intended month/day"를 기준으로 매 회차 계산.

## 완료 처리 후 next occurrence 생성 규칙
1. 사용자가 "완료"를 탭한다.
2. 현재 예약된 알림(notificationId) 취소.
3. `completedCount += 1`, `lastCompletedAt = now`.
4. `repeatType`이 `once`면 항목 종료 (UI에서는 "완료됨"으로 표시 또는 자동 삭제 중 택1. MVP: 자동 삭제하지 않고 "완료됨" 표시 후 24시간 뒤 리스트에서 숨김).
5. `repeatType`이 반복이면 위 규칙대로 다음 `dueAt` 계산.
6. 다음 `dueAt`이 `now`보다 과거면 그 다음 회차로 한 번 더 전진 (드물지만 오래 앱을 안 연 경우). 이 전진은 "과거가 아닌 첫 회차"가 나올 때까지 최대 365회 루프 후 중단.
7. 새 `dueAt`으로 알림 재예약. 새 `notificationId` 저장.
8. Isar write는 트랜잭션으로 묶는다 (`item update` + `notification 재예약`이 원자적이지는 않지만, Isar write 완료 후 알림 예약 실패 시 재시도 큐에 넣고 앱 resume 시 재시도).

## Edit 시 알림 재예약 규칙
1. 사용자가 항목을 저장(수정)한다.
2. 기존 `notificationId`가 있으면 **반드시 먼저 취소**한다.
3. 새 `dueAt`으로 알림 재예약.
4. 새 `notificationId`를 저장 (Id를 `item.id` 그대로 재사용하므로 새 schedule이 기존 것을 덮어쓰지만, **`cancel → schedule` 순서는 유지**하여 누락을 방지).
5. 저장 필드 중 `dueAt` / `repeatType` / `title`이 바뀌지 않았으면 재예약 skip 최적화 가능 (선택 구현).

## Delete 시 알림 취소 규칙
1. 항목 삭제 시 해당 `notificationId`를 **반드시** 취소한다.
2. 삭제 후 Isar 레코드를 제거.
3. 실패 시(알림 취소 API가 false 반환) 로그만 남기고 레코드 제거는 진행. 남은 알림이 울리더라도 탭했을 때 해당 항목이 없으면 홈으로 폴백.

## Past time scheduling 처리 규칙
- **예약 시점에 `dueAt <= now`인 경우**:
  - `once`: 사용자 명시적 의도이므로 "이미 지난 시각"이라는 확인 다이얼로그를 띄우고, 확인 시 즉시 1회 알림을 띄우는 대신 **저장만 하고 알림은 예약하지 않는다**. 홈 리스트에 "기한 지남" 배지로 표시.
  - 반복 항목: `dueAt`을 다음 회차로 한 번 전진시켜서 예약한다. (daily/weekly/monthly/yearly 규칙에 따라)
- **앱 실행 시 점검**:
  - `app_open` 시 `dueAt <= now`이고 `repeatType != once`이며 알림이 발사되지 않은 항목을 스캔해, 다음 회차로 전진시키고 재예약한다. (알림 도달 실패 복구)
  - `once` 항목은 "기한 지남"으로 유지.

## Timezone 및 기기 시간 변경
- 기기 타임존이 바뀌면 이전 예약 시각은 **UTC 절대시각 기준**으로 유효하다.
- 사용자가 "매월 25일 09:00"로 등록했는데 타임존이 바뀌어 실제로 현지 다른 시각에 울리는 현상은 MVP 허용 범위.
- `app_open` 시 현재 기기 타임존과 저장된 예약 시각을 비교해 현지 시각이 크게 어긋나면(예: 3시간 이상) 사용자에게 "타임존이 변경되었습니다. 알림 시각을 확인해주세요" 토스트를 띄운다. (선택 구현)

## 다중 알림 (하루 전, 1시간 전 등)
- **MVP 범위 밖.** 항목당 다음 1회만 예약한다.
- 사용자가 "하루 전" 알림을 원한다면 별도 항목으로 등록하도록 안내한다. (임시 해결)
- MVP 이후 우선순위 높은 확장 후보.

## 권한 요청 시점
- 앱 첫 실행 즉시 요청하지 않는다.
- **첫 항목을 저장한 직후**에 "이 항목의 알림을 받으시려면 권한이 필요합니다" 맥락으로 요청한다.
- 거부된 경우 홈 상단에 영구 경고 배너 표시 + 설정 앱 딥링크.
